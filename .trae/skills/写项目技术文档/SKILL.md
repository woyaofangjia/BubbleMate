# 写项目技术文档

## 何时调用
- 用户要求撰写或更新技术文档（架构说明、模块说明、API 文档、设计决策、实验报告）
- 完成阶段性开发后需要沉淀文档
- 用户提到"记录设计决策""整理实验数据""写 README/架构文档"

## 核心原则（分层 + 精简）
1. **分层**：项目级 → 模块级 → 接口级，按需展开，不重复
2. **精简**：只写代码无法自表达的内容，删除废话与冗余注释
3. **真实**：实验数据必须来自真实运行，禁用臆造数字或精美占位
4. **同步**：文档随代码变更同步更新，过期内容立即删除而非保留
5. **权衡**：设计决策必须记录选型理由、被放弃的方案、取舍代价

## 文档目录约定（硬约束）
- `docs/KEY_DESIGN_DECISIONS.md` — 关键设计决策，含权衡分析
- `data/experiment_results.json` — 实验结果，真实运行数据
- `README.md` — 项目入口，简介 + 快速启动
- `docs/architecture.md` — 整体架构与模块划分
- `docs/api.md` — 对外接口契约
- 模块级文档就近放在模块目录内，避免集中臃肿

## 文档分层结构

### 1. 项目级（README.md / docs/architecture.md）
- 项目目标与痛点（一句话）
- 技术栈与版本
- 模块划分图（用文字或 Mermaid）
- 快速启动命令
- 架构图：数据流 + 核心组件，不画细节实现

### 2. 模块级（模块目录内 .md）
- 模块职责（一句话边界）
- 对外接口（输入/输出/副作用）
- 依赖的上游模块
- 关键实现取舍（只写非显然的决策）

### 3. 接口级（docs/api.md）
- 路径 / 方法 / 请求参数 / 响应结构
- 错误码与边界行为
- 示例请求与响应（真实数据）

### 4. 设计决策（docs/KEY_DESIGN_DECISIONS.md）
每条决策包含：
```
## 决策标题
- 背景：解决什么问题
- 方案：选了什么
- 备选：被放弃的方案及原因
- 代价：该方案的已知缺陷或风险
- 决定时间：YYYY-MM-DD
```

### 5. 实验报告（data/experiment_results.json）
- 实验目的、参数、运行环境、真实数据点、结论
- 不写主观评价，只写可复现的量化结果

## 工作流程
1. 先读相关代码与现有文档，确认未覆盖的空白点
2. 与用户确认文档类型与目标读者（开发者/使用者/评审者）
3. 按上述分层结构填充内容，控制在"够用即停"
4. 引用代码位置使用文件链接：[文件名](file:///绝对路径#L起始-结束)
5. 完成后自检：是否有臆造数据、是否有与代码冲突的描述、是否冗杂可删

## 风格禁忌
- 不写"本系统是一个强大的、优秀的"等空话
- 不复制粘贴代码块到文档（用文件链接引用）
- 不写过度配置化、泛泛而谈的章节
- 不为未来可能用到的功能预留章节
