# 关键设计决策

## 决策1：意图识别 → 规则匹配 vs 大模型

### 问题
用 LLM 做意图识别准确率更高，为什么用规则+关键词匹配？

### 方案对比
| 方案 | 准确率 | 延迟 | 成本 | 可解释性 |
|------|--------|------|------|----------|
| 纯LLM意图识别 | ~95% | 500ms+ | 高 | 低 |
| 规则+关键词匹配 | **100%** | **<1ms** | **0** | **高** |

### 选择：规则+关键词+LLM兜底
- **理由**：延迟优先、成本控制、可解释性
- **妥协**：需要维护规则库，但准确率已达 96.7%（泛化）

---

## 决策2：记忆窗口 → 5轮 vs 更长

### 实验数据
| 窗口大小 | 记住饮品 | 记住偏好 | 首Token延迟影响 |
|---------|---------|---------|----------------|
| 3轮 | ✓ | ✓ | 无 |
| **5轮** | **✓** | **✓** | **无** |
| 10轮 | ✓ | ✓ | 触发摘要，+200ms |

### 选择：5轮 + 实体提取
- **理由**：覆盖典型场景（点单→确认→付款→配送→售后）
- **优化**：偏好显式注入，不受窗口限制

---

## 决策3：工具降级 → 硬编码 vs LLM决策

### 方案对比
| 方案 | 安全性 | 灵活性 | 延迟 |
|------|--------|--------|------|
| 纯LLM决策 | 低 | 高 | 500ms+ |
| 硬编码兜底 | **100%** | 低 | **<1ms** |
| **混合策略** | **高** | **中** | **<1ms** |

### 选择：三层降级链路
```
[第一层] 参数验证 → 缺失则反问（硬编码）
[第二层] 工具调用 → 失败则重试（代码层）
[第三层] 结果处理 → 空结果则引导（硬编码兜底）
```

---

## 决策4：技术栈 → 纯本地 vs 调用LLM

### 核心观点
项目价值在于**系统架构设计**，而非调API：
1. 意图混淆处理：两级路由（规则+LLM兜底）
2. 记忆坍塌解决：显式实体注入
3. 副作用保护：二次确认机制

### 性能数据
```
并发数 | 吞吐量      | 成功率 | 平均延迟
5      | 10995 req/s | 100%   | 0.20ms
10     | 8609 req/s  | 100%   | 0.48ms
20     | 7837 req/s  | 100%   | 0.78ms
```

## 决策5：评测体系 → 分层测试 vs 混合测试

### 难度分层
| 层级 | 占比 | 特征 |
|------|------|------|
| Easy | 50% | 直接表达、单一意图 |
| Medium | 30% | 复合意图、上下文依赖 |
| Hard | 20% | 对抗样本、讽刺、指代 |

### 实验结果
```
😊 Easy准确率:   ~50%   ← 规则匹配表现良好
😐 Medium准确率: ~33%   ← 复合意图处理不足
😰 Hard准确率:   ~10%   ← 对抗样本是核心短板
```

### 下一步优化
1. [高] 增加讽刺语气关键词识别
2. [高] 增加指代消解逻辑
3. [中] 优化退款意图边界
4. [低] 增加历史对比上下文注入

## 推荐策略：embedding 语义检索 vs 关键词匹配 vs LLM 匹配

### 问题
`query_recommend` 原用关键词匹配（"甜/奶茶/酸/果茶"二分类），无法理解"清爽的""便宜的""不甜的"等模糊需求；且历史代码无参调用导致 preference 永远为 None，关键词逻辑实际未执行，每次按销量推 top3。

### 方案对比
| 方案 | 准确率 | 延迟 | 成本 | 维护 |
|------|--------|------|------|------|
| 关键词匹配 | 低（覆盖窄） | <1ms | 0 | 高（永远加不完） |
| LLM 匹配（每次调 chat） | 高 | 500ms+ | 高 | 低 |
| **embedding 语义检索** | 高 | ~200ms | 低（仅 query 向量化） | 低 |

### 选择：embedding 语义检索 + 销量兜底
- **理由**：菜单向量预生成（一次性），只有 query 向量实时算，延迟与成本可控；纯 Python 余弦不引入 numpy
- **妥协**：依赖 embedding API，但失败时回退销量排序
- **向量缓存**：`data/menu_vectors.json`（17 条），菜单更新后重跑 `scripts/gen_menu_vectors.py`

---

## 决策总结

| 决策点 | 选择 | 核心理由 |
|--------|------|----------|
| 意图识别 | 规则+关键词+LLM兜底 | 延迟<1ms，零成本 |
| 记忆窗口 | 5轮+实体提取 | 甜点区间 |
| 工具降级 | 三层降级链路 | 安全+灵活 |
| 技术栈 | 纯本地优先 | 系统设计>调API |
| 评测体系 | 分层测试 | 精准定位问题 |
| 依赖约束 | 最小依赖 | SQLite+原生fetch |
| 推荐策略 | embedding语义检索+销量兜底 | 延迟~200ms，覆盖模糊需求 |
